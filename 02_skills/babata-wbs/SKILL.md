# Babata WBS

把用户的 WBS 意图交给现成工具，不另造计划系统。飞书多维表格是任务权威；
本 Skill 不创建本地主库、同步、Goal、调度器，也不启动知识宇宙收集/清洗。

## 先读取现有操作知识

- 从目标宿主的已安装 Skill 目录定位并完整读取 `feishu-wbs-task-management/SKILL.md`：
  它是本人的表坐标、字段、任务 ID、循环任务与复盘约定的唯一维护源。
- 读取 `lark-base/SKILL.md`，认证问题再按 `lark-shared` 路由。依赖缺失时明确指出，
  不猜表坐标、不改为飞书原生 task，不复制一套私有配置补洞。
- WBS 业务约定沿用既有源；CLI 语法以当前 `--help`、真实 schema 和当前 lark-base 为准。
  旧版 select 字符串、分页上限、固定 sleep 或清空日期写法不是跨版本保证。
- 私有坐标只从上述本地源或用户指定的 Git 外配置取得；凭据交给原 CLI。
  任务导出、日志、临时 payload 与验证回执放在 Git 外数据根，不进入仓库。

## 识别本次请求

| 用户说法 | 动作与边界 |
| --- | --- |
| 今天做什么、查待办、WBS 复盘 | 查询并报告；复盘建议不自动改表 |
| 更新下我的 WBS、根据目前进度刷新 WBS | 按本次明确关联的进度核对记录，只写有证据的差异 |
| 新建个待办，xxx、加个任务 | 按现有 ID 约定先查已有任务，再创建；内容不明确才询问 |
| 只看预览、dryrun | 仅形成变更预览；任何 CLI 写命令都带 --dry-run，不自动转实写 |

这些话语是触发条件，不是缺少正文时凭空造任务的授权。明确的更新/新建不反复逐项审批；
纯建议或整体重排沿用原有确认约定。一般的代码计划、Issue 拆分不因出现“任务”就写 WBS。

## 复用 CLI 完成操作

1. 普通查询直接查指定 WBS，不先遍历无关历史。按日期/状态用 `base +record-list`，
   不用要求非空 keyword 的 search 代替结构化过滤；投影所需字段，按当地日期及 Base 时区处理。
   全局复盘必须读取完整匹配范围；`has_more=true` 时按 `next_offset` 继续，未结束则标局部。
2. 写入或依赖类型的筛选前检查 `base +field-list`。本轮按任务 ID 解析 native record_id；
   同名不当唯一键，重复 ID/目标歧义只停住该项，不拿旧输出里的裸 record_id 猜。
3. 从本次指令或明确关联证据推导最小差异。建 Issue 不等于实施完成；不臆测任务关系、
   日期、优先级或完成。相同值不提交；保留摘要已有内容和无关字段，循环完成不因重投再加次数。
4. `base +record-upsert` **无 --record-id 是新建，有则更新；不是按业务键自动 upsert**。
   创建先查重；存在则返回现有任务，需更新时按明确意图处理。select 按 schema 使用数组，
   JSON 为顶层字段映射，不包 fields；不写只读字段，不为操作去改表结构。
5. dry-run 对已确定目标只给变更预览，不实写、不冒充已查重；请求构造测试可用合成坐标，
   但不能用测试结果证明真实鉴权/schema/资源可用。
   PowerShell 中保持 filter conditions 为嵌套元组，避免数组压平；大 JSON 按 CLI 支持传入。
6. 实写前重查涉及字段，变化时报告冲突；无原子条件更新就不承诺消除竞态。同表串行提交。
   完成本轮相关写入后统一回读；异步未可见时有限重查，不盲目重复写。超时结果未知先核对，
   不重复新建或计数；无法确认则如实保留未知。缺权限不静默切换身份，不自动登录。

## 报告

每项使用“任务 ID + 人话标题”，列变化、未变化、歧义/失败/未知及下一动作。
区分 Skill 被发现、请求 dry-run、真实读写回读；只报告实际验证到的层次。
不要输出凭据、本地身份标识或完整无关任务数据。
