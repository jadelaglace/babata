## 1. 职责

本文定义 `DOC-WORDING`、`DOC-WORDING-RECOVERY`、`DOC-ACTIVE-PLAN`、Requirements、Usage 和证据
之间的稳定读写生命周期。它不保存当前任务内容、产品需求、批次事实或完成证据。

治理目标是同时避免两种失败：最新目标只留在对话中而在压缩/挂机后丢失；所有原话、Agent 思考
和完成历史都永久堆在常用文件中，最终让真正目标无法读取。

## 2. 三层恢复结构

| 层 | 作用 | 正常读取 | 写入方式 | 清理方式 |
| --- | --- | --- | --- | --- |
| `DOC-WORDING` / 00_b | 当前仍有效、轻度整理的用户意图 | 需求/架构工作日常读取 | 任务终端后从已确认输入维护 | 已完全覆盖、过时且无当前张力的内容移出；逐字证据仍在 00_c |
| `DOC-WORDING-RECOVERY` / 00_c | 逐字输入与绝对必要的已归因上下文 | 仅严重阻塞、漂移、冲突、恢复/审计失败时 | 新产品输入 append-first 原样捕获；终端后补元数据 | 不因任务完成删除唯一证据；用状态/覆盖关系和索引降噪 |
| `DOC-ACTIVE-PLAN` / 04_f | 当前工作、下次开工队列、临时子计划、恢复入口 | 每次继续工作和上下文恢复先读 | 新通用待办、阶段结论、轮次终端及时更新 | 长期后果提升后删除成功且无义务的临时项；异常项标终态保留；只按 promotion policy 晋升 |

Requirements 是当前可执行产品需求；Usage 只保存真实交付状态；Git 外 receipt 保存具体运行证据。
三层恢复结构都不能替代这些权威。

## 3. 新输入的第一动作

0. 每次完整恢复边界，包括新 session、上下文压缩、可能丢失控制权或上下文的 Agent/任务交接或
   中断、执行状态不确定的长时间暂停，以及用户明确发出“继续”“恢复”“接着做”等指令时，
   在任何状态写入前先调用环境可用的
   Goal/task-state API，再立即读取 `DOC-ACTIVE-PLAN` 并核对唯一 `CURRENT-ACTIVE` 和 terminal 状态；
   禁止从摘要或最后可见消息猜测。摘要、断点或最近可见片段未包含的信息一律视为 `unknown`，
   不能推断为“未完成”；“继续/恢复”只授权继续既有 Goal，不授权选择新的 active 或队列项；
   当前 turn、上下文和 governing task 身份完整，且明确返回结果的普通同步工具、命令或 API 失败只在
   原地处理或重试，不构成完整恢复边界。有状态操作结果不明时先核对该外部状态；只有控制上下文或
   governing task 身份也可能丢失时，才重新执行完整钩子；
1. 产品特定的意图、纠正、价值判断、开放问题：在任何回溯、检索或分析前原样追加到 00_c；
2. 跨项目协议、通用待办、只读审计或执行顺序：若改变正在执行的路线，写入当前活动项；否则在
   任何回溯前插到“下次开工队列”顶部，不静默打断或覆盖当前任务；
3. 同一句兼有两者时分别捕获，并用一个来源锚点关联，不能为了少写一处丢失其中一层；
4. 捕获只做最小定位，不先润色、归纳、判断有效性或提升为 requirements；00_c 的新捕获使用带
   唯一 `DFC-*` 身份的标准 `DOCS-FIRST-CAPTURE` 标记，相关 active-plan 项引用同一 ID，以便终端时
   只维护该条目的元数据、索引和执行关联；
5. 完成恢复身份核对和必要捕获后，才按 DOC-INDEX、00_b、Requirements 的顺序解释产品，再向下
   读取完成本次任务真正需要的权威；队列只提供未来入口，不进入当前执行选择。

## 4. Goal 与状态转换硬约束

恢复状态分为三个互补层级。先查 Goal/task-state、再读唯一 Active Plan 是强制读取顺序；读取顺序
不等于让旧状态覆盖实时层：

1. **实时对话层**：当前交互里的最新明确指令、实际结果和完成汇报。它最及时、动作优先级最高，
   也最容易被上下文中断、压缩摘要错序或残片污染，因此必须结合可见结果和下两层核验实例身份。
2. **Goal 运行层**：跨对话、跨压缩保存短中期 Goal 的 scope 与运行状态。它通常与 Docs 中的一条
   active scope 对齐并代表真实方向，但可以 `paused` 以避让实时新指令；暂停保留身份和义务，不授权执行。
3. **Docs 持久层**：保存同一 scope 的计划、状态、下一步、终态和不可越过的红线。它最抗噪音和
   漂移，但可能比实时层和 Goal 层落后一个终端回写窗口。

恢复时核对三层是否描述同一指令/阶段实例。若实时对话层已有对应结果并明确汇报完成，而 Goal 或
Docs 仍标为进行中，且差异可由尚未执行的终端回写解释，则判定为**回写滞后**：不得重新执行业务
动作、收尾、测试或发布；只补写 Goal/Docs/证据的剩余终端维护，并将对应 Goal 或阶段推进到已经由
结果证明的状态。Docs 中“仍在做”不能覆盖实时层已经发生的完成事实。

若实时层没有可信的新指令或结果，才按 Goal 运行状态与 Docs 的当前下一步继续。若 Docs 已标记
terminal，或成功项已依终端维护规则从 Active Plan 清理，不得因实时上下文缺失、摘要残留或当前
看不到该条目而反推未完成。压缩摘要、交接文字、旧消息和工具断点不构成第四层；它们只能帮助定位
三层证据，不能独立授权动作或制造新的指令实例。同样的自然语言只有被用户在恢复后重新明确发出，
才形成新的指令实例。

- 完整恢复边界不是新任务授权。新 session、handoff、控制上下文可能丢失的中断和用户的
  “继续/恢复”都必须执行同一核对；不能把调用栈断点、最后一条 commentary 或交接摘要当成 Goal。
  已明确返回且当前 turn/任务身份完整的普通工具失败不是再入场，不重复查询 Goal 或 Active Plan。
- 恢复后的首个执行动作必须由三层核对结果产生：实时层有新指令时服从新指令；实时层已完成而
  Goal/Docs 滞后时只做终端回写；否则才由 `active` Goal 与唯一 `CURRENT-ACTIVE` 对齐后的当前
  “下一步”提供动作。任何已有完成结果或 terminal 状态的旧实例不得重放。
- 当前 active goal/item 和 `resolved/superseded/closed` terminal 状态默认不可变。上下文压缩、摘要
  缺项、Agent 怀疑、想重新审计或发现实现还能改进，都不是状态转换授权。
- active 只能因三类依据改变：用户明确覆盖当前 Goal；当前项到达合法终端后晋升明确标记
  `auto-promote` 的队列项；出现真实阻断并由用户或既定 authority 明确授权重排。标记
  `requires-explicit-resume` 的队列项不能因前项 terminal 自动晋升。仅发现阻断时先把当前项标为
  `blocked`，不能自动换成另一个 active。
- terminal 项只能因用户明确要求重开，或新的可核验证据证明原 terminal 本身失效而重开；必须保留
  原 terminal 元数据，追加 `reopened_by`、证据和影响范围，不能把原状态静默改回 `active`。
- 环境提供线程/外部 Goal 时，当前活动项必须记录 Goal 锚点和状态转换依据。两者不一致时保持双方
  原状态，先依据最新明确用户指令或 authority 解决冲突；无法解决时请求用户决定，禁止先写新 active。
- 首次建立 governing Goal 与覆盖一个仍在执行的 Goal 是两种不同转换：用户明确启动新 Goal 使用
  `user-explicit-goal-start`；只有用户明确替换当前 active Goal 时才使用
  `user-explicit-goal-override`。先前工作已经 terminal，不得被描述成仍在执行并遭到覆盖。
- 用户编号子任务或声明阶段到达终端后，先回写对应阶段状态和下一动作，再开始下一项；不能用连续
  执行为理由跳过终端维护。

## 5. Agent 阶段结论与临时子计划

Agent 不记录全部思维过程，只在以下时机回写对应活动项：

- 分析形成足以改变后续路线、范围、合同或风险处理的阶段结论；
- 一个完整执行轮到达声明终端并形成终端矩阵/缺陷账本；
- 发现共享阻断、输入漂移、权限边界或继续执行会使证据失真；
- 即将进入长时间跑批、大范围检索、上下文密集阶段或交接之前。

每个当前活动项最少保存：来源锚点、用户目标、当前状态、目标终端、不改变的边界、临时子计划/
阶段结论、下一动作和必要证据入口。队列项只保存恢复所需的来源、目标、已知阶段结论、下一动作
和入口；晋升为当前项后再补齐执行终端。阶段结论必须标为 Agent 结论，不能写入 00_b 冒充用户
意图；只有用户采用或权威过程确认后才传播为 adopted decision。

避免两种极端：不回写任何中间结论导致压缩后重来；每次工具调用或局部测试都写计划导致控制面
比工作本身更重。回写阈值是“失去它是否会让下一位 Agent 走不同路线或重复大段工作”。

## 6. 文件规模与结构

- active plan 先写“当前活动项”，再写“下次开工队列”：当前活动项最多一个；队列通常只保留少量
  仍有义务的条目，不得维护第二套 backlog。每个队列项必须明确标记 `auto-promote` 或
  `requires-explicit-resume`；后者不是当前项终端后的默认下一项。新输入只有在不改变
  当前路线时才进入队列；改变当前路线时更新当前项。当前项内部使用有界临时子计划，不复制
  Requirements、Usage 或完整日志。
- 队列最多保留 5 项；超过该数量说明义务没有及时晋升、合并、完成或移入正式 backlog，必须先
  清理控制面，不能靠极短条目绕过全文件行数阈值。
- 队列项按用户明确优先级排列；没有明确优先级时，最新捕获的通用义务插在顶部。晋升时保留来源
  锚点和已有阶段结论，只改变执行状态和补齐终端，不重新回溯已经确认的事实。
- active plan 是恢复热路径，只保存动态状态并链接本治理，不复制稳定生命周期、Requirements、Usage、
  完整日志或成功历史。目标保持在一个屏幕内；硬上限为 120 行且 6,000 字符，任一超限都必须先执行
  终端提升与清理。字符上限防止超长单行绕过行数约束；规模约束不是删除有效信息的理由。
- 任意 Markdown 标题层级中的 `AP-*` 都必须是当前项或队列项的三级标题；不得用四级或更深标题把
  成功 terminal record、完成编年史或竞争计划藏在解析器之外。
- 00_b 按稳定意图主题组织，不按日期堆叠；建议保持约 80–250 行。超过约 300 行时审查是否混入
  历史方案、运行状态、实现细节或重复解释。
- 00_c 可以长期增长，但顶部必须有极简检索索引；优先按日期/决策簇追加。新条目只保存恢复必要
  内容，不把完整对话、工具日志或可从正式权威重建的解释倾倒进去。

## 7. 终端维护顺序

任务到达成功、失败、阻塞、中断或交接终端后，按以下顺序一次性维护：

1. 将 adopted decision、当前需求、稳定架构、实际 usage、运行证据和仍未解决的义务提升到其
   各自主权威；
2. 更新 00_b：保留仍有效意图和必要开放张力；删除已被完全覆盖的常用副本，但不动 00_c 原证据；
3. 若本任务曾写入 00_c，新条目补全 capture time/source、3–8 个极简检索词、状态和
   `superseded_by/resolved_by` 关系，并更新顶部索引；条目状态与索引状态必须一致，`active` 条目
   必须仍由 active plan 的同一 `DFC-*` 来源锚点承接，`resolved/superseded/recovery-only` 条目不得
   继续伪装成活动义务。纯通用待办没有 00_c 条目时不得为满足流程额外制造一条；任何情况下都不
   改写逐字引文；
4. 成功且无遗留义务：删除 active plan 中的临时活动项/子计划；只晋升排序最前且明确标记
   `auto-promote` 的队列项。`requires-explicit-resume` 项继续排队；没有可自动晋升项时允许
   `CURRENT-ACTIVE: none`，明确写“当前无活动项，等待授权”，不能用 held queue 填补 active；
5. 失败、阻塞、中断或仍有交接：保留活动项，标明终态原因、已有证据、下一授权/决定和恢复入口；
6. 运行 provenance、traceability、intent/plan governance mutation 及与变更风险相称的 broader gate。

直接用户证据、adopted decision、Usage、验收、失败恢复和 handoff 证据不因任务结束而删除。临时
锚点也不得在长期后果提升前删除。

## 8. 读取顺序

正常继续工作：

```text
线程/外部 Goal（若可用） -> DOC-ACTIVE-PLAN 的 CURRENT-ACTIVE -> DOC-INDEX -> DOC-WORDING ->
Requirements -> 所需下游权威；队列只读且不参与本次目标选择
```

若 Goal 为 `null/terminal`、`CURRENT-ACTIVE: none` 且实时层有明确的新用户指令，恢复核对到此结束，
直接按新指令所需的最小权威继续；不得为了确认“确实没有旧任务”再读历史、Usage、00_c 或整个文档链。
只有 Goal 与 Active Plan 不一致、活动项存在或当前任务语义确实需要时，才继续展开后续权威。

只有严重恢复条件成立时：

```text
上述链无法推进 -> 00_c 极速索引 -> 命中的原话/已归因上下文 -> 回到当前权威修复冲突
```

不得因为 00_c 更“原始”就每次从头阅读；它是最后关头的恢复证据，不是更高频的第二 requirements。
