## 2. 当前有效意图

### 2.1 核心目的

- Babata 以用户为中心，把散落在平台、设备和外部资料库中的个人资料省心取回、忠实保存、
  清洗理解并沉淀为可长期使用的个人知识宇宙。
- 真实内容、真实路线和用户最终能使用的结果优先于宏观协议、漂亮接口和抽象完整。
- 用户负责需求、优先级、价值判断和最终验收；明确范围内的调研、执行、付费调用、证据和收敛
  由 Agent 承担，不把日常技术审批负担推回用户。

### 2.2 四段链路

```text
收集与初步归档 -> 独立多模态清洗 -> 消化/沉淀/建模/管理 -> 子库、传播与输出
```

- 逻辑分层不等于提前拆仓、拆服务或设计跨模块 API；先由一个本地优先系统跑通真实闭环。
- 输出是否未来成长为独立应用仍是开放选择，不为概念完整提前拆分。

### 2.3 长期价值判断

- 原件和第一方内容最重要；清洗尽量保持原味，机器建议不能冒充人工事实。
- 课程信息可以高密度压缩，生活和记忆资料应保留更多时间、设备、路径和当时上下文。
- Obsidian 等输出是可删除重建的阅读视图，不是新的权威存储。
- 正式系统应让人用起来，而不是要求用户长期操作复杂 CLI 或逐项审批。
- 资料、知识、案例、日志和感悟共同构成以“我”为中心、可以持续演化的个人知识宇宙。

## 3. REQ-01：本地优先与一次授权

1. 正式运行数据、媒体、数据库、模型输出、日志、秘密和用户资料必须位于 Git 外数据根。
2. 用户给出明确来源、资料或处理范围后，Agent 应在该范围内连续完成可逆的调查、准备、重试、
   处理、成本记录和验证。
3. 只有登录/授权不可替代、范围语义不清、不可逆删除、安全风险、大额无边界调用或用户价值判断
   才暂停请求用户决定。
4. 日常使用现有 Babata release 不要求 Issue/PR；改变产品合同、schema、行为或已决定修复 Bug 时
   才进入正式开发流程。

## 4. REQ-02：来源收集与主权取得

1. 优先官方批量导出、成熟 CLI/SDK、浏览器和已有工具；仅为已证明缺口做最窄实现，手工是最后回退。
2. discovery/candidate 不等于收集；只有明确选择并通过边界校验的对象才能进入正式 C0 writer。
3. 收集必须保留来源身份、正文、附件、时间、层级、原始定位、完整性方法和逐项结果。
4. 成功、失败、跳过、不可访问、removed、changed 和 unchanged 必须可辨别；重试只影响失败对象，
   unchanged recollection 不制造新版本。
5. Agent 默认不得操作微信 UI；除非用户另行明确授权。暂缓范围保留上游归档和清单，不冒充完成。
6. 来源路线必须按真实工具证据、授权条件、限制和 runtime capability 选择，不把 fixture 当正常路线。

## 5. REQ-03：C0、第一方内容与唯一 writer

1. C0 保存用户拥有或有权保存的原始资料；第一方创作、批注和感悟走同一套身份、来源和版本原则。
2. 正式身份、revision、状态和关系只能由 Rust application/core 经 infrastructure 写入。
3. Skill、脚本、Agent、模型、浏览器、临时 handoff 和输出视图只能提供候选或调用正式能力。
4. 事务失败不得产生伪 ready；数据库记录、managed asset 和 read-back 必须一致。
5. 修订只在真实内容发生变化时追加；普通评论、附件、日志或机器再分析不被强迫伪装成 `v2`。

## 6. REQ-04：忠实清洗与 C1B

1. 清洗独立于收集，读取稳定输入并生成可追溯派生，不覆盖 C0 或外部原件。
2. C1A 保存完整、忠实、可检查的文字派生；处理器、模型、配置、输入范围、限制和输出 hash 可追溯。
3. C1B 在完整文字基础上判断哪些图片、音频、视频片段或附件对理解不可替代，不按固定数量凑模态。
4. 没有必要新增媒体时也可以形成完整 C1B 判断；摘要不能替代完整文字。
5. 多种处理结果可以并存；失败项隔离、可重试，派生可删除重建。
6. 付费 provider 可以用于质量和效率；必须记录模型/版本、地域、计量、价格时间、实际 usage 或明确
   标注的估算成本，免费额度未知保持 unknown。

## 7. REQ-05：个人知识宇宙

1. 个人知识宇宙包含知识、案例、日志、感悟和它们之间有依据的显式关系。
2. 时间、空间、物质、意识是稳定但可重叠的世界观基石，不是四选一内容桶；改变基石需显式版本化。
3. Discipline/Branch 形成有类型、受约束的多父 DAG；Course 保持独立身份，通过 `covers` 关联 Branch。
4. MBA 等集合是非拥有型 lens/sublibrary；没有真实培养方案需求时不提前创建 Program。
5. 兴趣、战略和共识三种动态相关度分开；foundation intensity、confidence 和动态相关度不互相冒充，
   默认不强制合计 100%。
6. 机器可以建议类型、标签、关系、评分和高密度表达；未审阅建议保留 machine/unreviewed 身份。
7. 第一方日志与感悟必须能引用知识、案例和当时证据，形成可追踪的认知演化而不是孤立笔记。

## 8. REQ-06：检索、子库和输出

1. 用户能够按正文、来源、时间、类型、关系和语义检索、回看并组织资料。
2. Sublibrary 是版本化的范围、查询和组织定义；物化内容是可重建视图，不复制第二套知识权威。
3. 输出必须记录输入身份、范围、builder/profile、版本、限制和输出完整性；删除/重建输出不改变上游。
4. Markdown、JSON、Obsidian、Web 或未来格式按真实用途启用；未实现能力保持 unavailable/unplanned。
5. 课程输出使用唯一 live；用户可见标题应表达内容或操作，不暴露内部 ID、`latest`、C2B 等字段式名称。
6. 知识正文只写知识；工作要求、存储解释、模型说明、验证步骤和控制面信息不能污染正文。
7. 课程图应兼顾结构、复习密度和真实内链；Mermaid/PNG 等具体 profile 由版本化输出合同管理。

## 9. REQ-07：外部主权库与 Backs 记忆档案

### 9.1 通用外部主权边界

1. 自带完整结构和上下文的外部库继续拥有其原件、目录和 native writer。
2. Babata 可以登记库身份、snapshot、对象、原路径、hash、权限和变更关系，并生成可重建导航。
3. 不要求所有外部对象先转换为正式 C0/C1；只有用户选定对象才走 promotion。
4. 通用 snapshot/diff/navigator 仍是候选方向，不能因 Backs 需求已采用就声明 capability 已实现。

### 9.2 `D:\Backs` 专用记忆档案目标

`D:\Backs` 不再被定义为永久不可修改的只读库，而是一个允许**留证后受控整理**的个人记忆档案：

1. 清理前冻结完整目录清单、稳定路径、时间、大小、强 hash 和结构截屏，形成可审阅 snapshot。
2. 字节完全相同的文件可以去重；默认保留能可靠判定的最旧实体，并保留其他设备/年份/路径 occurrence。
3. 同名、近似图片、不同压缩或内容不完全相同的文件不能作为精确重复自动删除。
4. 明确的缓存、临时文件、安装残留和无意义程序垃圾可以清理；删除候选必须有规则、证据和清单，
   优先隔离或进入可恢复位置，永久处置仍属不可逆边界。
5. 清理后再次固化目录树和结构截屏；前后 snapshot 共同形成“记忆宫殿”。
6. 截图默认视为可能的主动留存信号，而不是垃圾；应通过 OCR/视觉理解提取时间、主题和有用信息。
7. 有信息价值的截图、照片、文本和记录需要被 Babata 清洗、聚合并回链原文件、原路径和 snapshot。
8. Obsidian 建立唯一目录 `归档分析/`，按年份形成年度时间线、日常日志、重要事件、关注主题、
   截图信息、年度感悟和证据索引。
9. 日常日志是年度归档的证据基石；“年度精髓/感悟”是有依据的高密度总结，不能把模型推测冒充
   当年的真实想法。

状态：`adopted requirement / not implemented`。本次文档收束不执行 Backs 扫描、删除、清洗或发布。

## 10. REQ-08：恢复、备份和安全

1. C0、第一方内容、人工决定和必要 provenance 是恢复关键；C1/C2/C3 按声明策略验证或重建。
2. 备份必须加密、可校验，并在隔离目录完成真实 restore/read-back 后才能声称可恢复。
3. 恢复不得自动覆盖活动数据根；凭据不进入备份仓库，恢复后需要重新授权。
4. 密钥/凭据不进入普通语义处理链；只允许安全引用、完整性状态和专用安全库控制。
5. 删除原件或改变权威必须有明确授权、精确目标、预先证据和可恢复策略。

## 11. REQ-09：执行与文档治理

1. 多阶段或重复工作按完整 execution round 推进：冻结范围和输入，跑到声明终端，统一记缺陷，
   成组修复后从干净 staging 开新轮完整复验。
2. checkpoint、repair test、工程 gate、产品 TC 和用户 acceptance 必须分开。
3. 新治理输入先进入正确角色；Requirements、行为、验收、架构、状态、原话和计划各有唯一 authority。
4. 恢复先查询 Goal/task-state，再读取唯一 Active Plan；已关闭工作不得因摘要、压缩或旧状态重跑。
5. 当前文档聚焦真实需求和后续使用；P0-P9 历史、已 resolved 原话和批次细节进入归档、Git 或 receipts。
